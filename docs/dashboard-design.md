# Analytics 2.0 – Power BI Analytics Layer

## Overview

Power BI was used as the visualization and decision-support layer of Analytics 2.0.

The processed output from the Python analytics workflow was used to create interactive analytical views for incident categorization, operational trends, capability-level analysis, repetitive issue identification and drill-down investigation.

```text
Raw Incident Data
        ↓
Python Processing
        ↓
Categorization & Enrichment
        ↓
Analytics-Ready Dataset
        ↓
Power BI
        ↓
Operational Insights
```

> Original Power BI files, screenshots and enterprise datasets are intentionally excluded from this public repository to protect confidential information.

---

# 1. Incident Overview

The overview layer provided a consolidated view of incident activity.

Key analytical areas included:

- Incident volumes
- Level 1 categorization
- Level 2 categorization
- Incident trends
- Operational KPIs
- Category distribution

The objective was to provide a high-level understanding of:

> What types of incidents are occurring and where is incident volume concentrated?

---

# 2. Level 1 & Level 2 Analysis

The categorization output generated by Python was consumed by Power BI for hierarchical analysis.

```text
Total Incidents
      ↓
Level 1
      ↓
Level 2
      ↓
Detailed Issue Analysis
```

This allowed analysis to move from broad categories into more specific incident types.

Example:

```text
Storage
   ↓
Disk Capacity
```

The hierarchy supported both summary-level reporting and deeper analysis of specific issue categories.

---

# 3. Capability-Level Analysis

Following the V3 enhancement, capability information was included as an additional analytical dimension.

```text
Operational Groups
        ↓
Capability Mapping
        ↓
Power BI
        ↓
Capability-Level View
```

This enabled broader analysis across multiple operational groups belonging to the same capability.

The objective was to help capability leaders identify:

- Areas with higher incident concentration
- Common issue categories
- Trends within their scope
- Potential improvement opportunities

---

# 4. WAM – Repetitive Issue Analysis

The V4 Whack-a-Mole (WAM) output was incorporated into the analytics layer to highlight repetitive operational issues.

The analysis used:

```text
Configuration Item
        +
Level 2 Category
```

along with the 30-day trend calculation.

Power BI could then expose WAM classifications such as:

```text
Issue Increased
Issue Existing
Issue Decreasing
Issue Solved
```

This helped distinguish ordinary incident volume from recurring operational problems requiring attention.

---

# 5. Trend Analysis

Time-based analysis was used to understand how incident patterns changed over time.

Typical analytical dimensions included:

```text
Date
  +
Level 1
  +
Level 2
  +
Capability
```

This allowed users to investigate whether particular categories or operational areas were experiencing increasing or decreasing incident volumes.

---

# 6. Drill-Down Analysis

Power BI provided the ability to move from high-level KPIs into more detailed incident analysis.

Conceptually:

```text
Enterprise / Portfolio View
          ↓
Capability
          ↓
Level 1
          ↓
Level 2
          ↓
Configuration Item
          ↓
Detailed Incident Records
```

This supported both leadership-level monitoring and detailed operational investigation.

---

# 7. Role of Power BI in Analytics 2.0

Power BI was not responsible for the primary incident-classification processing.

The responsibilities were separated:

| Component | Responsibility |
|---|---|
| Python | Data preparation and processing |
| Regex / Mapping | Rule-based classification |
| Capability Mapping | Operational ownership enrichment |
| WAM | Repetitive issue and trend calculation |
| Machine Learning | Learned text classification |
| Power BI | Visualization, exploration and decision support |

This separation allowed Python to perform the analytical processing while Power BI focused on presenting the resulting information to users.

# 9. Public Portfolio Limitation

The original Power BI implementation was developed using enterprise operational data.

For confidentiality reasons, this repository intentionally does not publish:

- Original `.pbix` files
- Dashboard screenshots
- Original datasets
- Customer/account information
- Internal organizational structures
- Production KPIs
- Internal operational metrics

The architecture, analytical methodology and Python implementation are documented instead to demonstrate the technical approach without exposing confidential information.
